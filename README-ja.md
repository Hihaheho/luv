# luv

[English](README.md) | 日本語

luv はバージョン管理システムです。git や jj と同じように、変更をコミットとして記録し、履歴をたどり、三方マージで統合します。違いは、管理の単位が「行の並んだファイル」に限られず、「ID を持つオブジェクト」であることです。

alpha です。コマンド、API、ストアのフォーマットは互換性を保たずに変わります。

## どんな VCS か

### 管理するのはオブジェクト

luv が記録するのはオブジェクトで、種類は次のとおりです。

- text: テキスト。
- record: フィールドとコレクションを持つ構造化された値（JSON に近い）。
- binary: バイト列。本体は blob として別に保存される。
- conflict: 解消されていないマージ結果。
- deleted: 削除されたことを表す状態。

オブジェクトにはパスとは別にランダムな ID が付きます。パスは `title` というメタデータのひとつで、同一性には使いません。コアはこの前提で作ってあります。CLI はファイルのパスをそのまま `title` にして対応づけています。`luv mv` で移動したファイルは同じオブジェクトのままです。それ以外の方法で移動・改名したファイルは、ファイルの削除と追加として扱われます。

### マージはデータの形を見て行う

三方マージ（base / left / right）は、同じ入力なら必ず同じ結果を返す純粋な関数です。

- text は行単位で、histogram diff をもとにした diff3 でマージします。改行コードや空白の正規化はしません。バイト列はそのまま扱います。
- record はフィールドパスごとにマージします。スキーマが、パスごとに Scalar / Set / List / Text / Opaque のどれで扱うかを決めます。
- コレクションの要素には安定した ID があります。Set は追加と削除が要素単位で統合され、List は要素の順序も統合されます。両側が別々の順に並べ替えたときだけ、順序の衝突になります。

衝突は、ファイルにマーカーを書き込む形では表しません。`Conflict` オブジェクトとして記録され、衝突の種類（値、順序、削除と編集、テキスト領域、メタデータ）がそれぞれ残ります。メタデータの衝突は、たとえば両側が同じオブジェクトに別々の名前を付けたときに起きます。解消は、片側を採用するか、テキストまたは record を直接与えて行います。title が衝突しているときは title も与えます。

### 操作が履歴として残る

すべての操作は 1 つの SQLite トランザクションで実行され、途中で落ちても中途半端な状態は残りません。操作ログがあり、undo / redo ができます。

コミットは複数の親を持てます。HEAD は複数並び立つことがあります。

### ブックマーク

ブックマークは、コミットを指す名前です。チェックアウト中のブランチという考え方はありません。workspace はブックマークを 1 つ選択でき、そこで Record すると、そのブックマークが前に進みます。進むのは、呼び出し側が最新の状態を見ていて、新しいコミットが今の指す先の子孫であるときだけです。ブックマークには名前とは別の ID があり、改名しても同じブックマークのままです。

ブックマークの履歴は、変更不能な更新の DAG で、コミットと同じように端末間を運ばれます。状態は更新の集合だけから計算し、届いた順番には左右されません。フィールド（名前、指す先、存在）ごとに、最後にそれを書いた更新が値を決めます。2 台の端末で改名と移動をすれば両方が反映されます。別々の移動、削除と編集、別々の改名は、候補をすべて残した衝突になり、誰かが選ぶまでそのままです。両方が 1 本の履歴の上で前に進んだ移動どうしは、先にある方で一致します。2 台がそれぞれ同じ名前のブックマークを作ることもできます。luv はどちらかを選ばず、名前が重なっていることを知らせます。どちらかを改名・削除するか、片方をもう片方に統合（fuse）して解消します。ブックマークの変更の undo は、共有済みかもしれない更新を消さず、元に戻す新しい更新を書きます。repo の既定のブックマークも同じ仕組みで保持します。

### ID は鍵つきハッシュ

内容の ID（content / state / tree / commit / conflict / blob / bookmark update）は、リポジトリごとの鍵で HMAC-SHA256 をかけた値です。入力は正規化した CBOR で、同じ値は常に同じバイト列になります。スナップショットはオブジェクトの ID を引く Patricia 木で、挿入順に関係なく同じ根になり、コミット間で変更のない部分木を共有します。

同じ内容でもリポジトリが違えば ID は違います。blob の重複排除も、同じリポジトリの中だけです。

### ホストが組み込む前提のコア

コアのクレートはハッシュ計算と乱数、時計、デバイス ID をホストから受け取ります。リクエストとレスポンスの型は feature で TypeScript と Swift 向けの定義に書き出せます。CLI は、このコアを呼ぶホストのひとつです。

## 何ではないか

- git 互換ではありません。git のリポジトリを読み込めず、git のコマンドも使えません。
- サービスではなく、専用のサーバーも持ちません。端末同士はリモートを介して履歴を交換します。リモートは追記専用のログと blob 置き場で、共有ディレクトリか、`luvcs-protocol` のメッセージを話すプログラムです。ストアは作業ツリーの `.luv/` にある SQLite ファイルです。リポジトリの export と import もできます。
- チェックアウト中のブランチはありません。ブックマークはコミットに名前を付けますが、勝手には動きません。pull でブックマークが手元の作業ツリーに移ることはなく、Record で進むのは選択したブックマークだけです。
- 「ディレクトリ内のすべてのファイル」を対象にしません。CLI は `Luv.eure` に書いた glob に一致するファイルだけを見ます。一致しないファイルは、保存も一覧も削除もされません。
- 行マージだけではありません。構造を持つ値は、構造のままマージします。逆に、テキストの意味やコードの構文を理解したマージはしません。
- 暗号化や権限管理の仕組みではありません。リポジトリの ID 鍵は平文でストアに入り、ストアのファイルは所有者だけが読めます。リモートのログにもこの鍵が入ります（pull する端末が取り込む内容を検証できるように）。リモートは中身と同じ秘密度で管理する必要があり、暗号化はリモート側の仕事です。export したアーカイブも同じ扱いが必要です。

## CLI

`luv` コマンドは現在、次のものだけを持ちます。

```
luv init --include "**/*.md"
luv status
luv diff
luv commit -m "message"
luv mv <from> <to>
luv log [--from <rev>]
luv restore [--commit cmt_...] [paths...]
luv merge cmt_...
luv resolve <path|obj_...> [--take ours|theirs] [--title <path>]
luv undo
luv redo
luv bookmark list [--all]
luv bookmark create|move <name> [--commit <rev>]
luv bookmark rename <name> <new-name>
luv bookmark delete <name> [--new-default <name> | --clear-default]
luv bookmark fuse <name> --into <name>
luv bookmark select <name> | --none
luv bookmark default <name> | --clear
luv bookmark resolve <name> [--commit <rev>] [--rename <name>] [--keep | --delete]
luv remote set --path ../shared      # または --command "program args"
luv push
luv pull
```

`init` は `Luv.eure` を書きます。

```
repo = "notes"
include = ["**/*.md"]
```

`remote set` は `.luv/remote.eure` をストアの隣に書きます。ファイルと一緒に渡されることを想定した `Luv.eure` はコマンドを指定できず、`.luv`・`.git`・`.jj` はどの階層でも追跡も restore もされないので、他人の履歴から来たファイルでリモートを書き換えたり `luv` にコマンドを実行させたりすることはできません。`push` はリモートがまだ持っていないものを送り、衝突しません。`pull` はリモートの履歴を取り込み、手元のファイルには触れません。リモートは秘密と同じ扱いで信頼する必要があります。リモートから初めて届いた repo の ID 鍵は、そのリモートが与えたものをそのまま受け入れるので、信頼できるリモートからだけ pull してください。2 台目の端末は、`remote set`、`pull`、`init --repo <name>`（pull した repo に接続します）、`restore` の順で始めます。

同時にコミットされたあとの repo は複数の HEAD を持ち、`luv log` はそのすべてを表示します。`merge` は、そのうちの 1 つを最後のコミットに統合し、統合結果のファイルを書き出します。衝突したファイルは、衝突した箇所を `<<<<<<< left` / `>>>>>>> right` のマーカーで囲んで書き出します（衝突そのものは、マーカーではなく `Conflict` オブジェクトとして保存されたままです）。`status` はそのファイルを `C` と表示し、`resolve` で解消するまで `commit` は拒否されます。`resolve` は既定ではディスク上で編集したファイルの内容で解消し、`--take` を付けると片側をそのまま採用します。作業ツリーのファイルにならない衝突（include の外にあるものなど）は `obj_…` の ID で表示され、`--take` で解消します。`undo` と `redo` は操作ログ（コミット、統合、解消、保存）を 1 つずつ戻し・進め、ファイルも書き戻します。`merge`・`undo`・`redo` は、ディスク上のファイルが保存済みの内容と違うあいだは実行を拒否するので、手元の編集を上書きすることはありません。

`mv` は追跡中のファイルをディスク上で移動し、新しいパスで同じオブジェクトとして保存します。そのため統合では、古いパスのまま加えられた編集も移動先のファイルに反映されます。2 台の端末が 1 つのファイルを別々のパスへ移動すると title の衝突になり、`resolve --title` で解消します。手で移動済みのファイルを記録するだけにも使えます。移動は `commit` で記録されるまで `status` に `R <from> -> <to>` と表示され、どちらかのパスを指定した `commit <path>` でそれだけを記録できます。`mv` が移動できるのはファイル単位で、ディレクトリはまだ扱えません。

コミットを受け取る場所（`<rev>`、`restore --commit`、`merge`、`log --from`）では、ブックマーク名や `bmk_…` の ID も使えます。`luv commit` は選択中のブックマークを前に進め、`luv log` は各コミットに付いているブックマークを表示します。2 つのブックマークが同じ名前を持っているときや、指す先が衝突しているブックマークは、推測せずにエラーにします。`bmk_…` の ID を使い、`rename`・`fuse`・`resolve` で解消してください。シンボリックリンクは追跡せず、警告を出して飛ばします。

## 構成

| クレート | 内容 |
|---|---|
| `luvcs` | コア。オブジェクト、ID、ツリー、マージ、ローカルストア、リクエスト API、リモート、push と pull |
| `luvcs-cli` | `luv` コマンド |
| `luvcs-macros` | FFI 向け型を生成する属性マクロ |
| `luvcs-protocol` | luvcs とリモートの間のメッセージ。ログのエントリ、blob のチャンク、リモートの設定 |

## 組み込みと remote の契約

push は remote が通知するエントリ、blob チャンク、Append 件数の上限に従います。
上限を省略した remote には、既定値の 1 MiB、4 MiB、256 件を使います。
単独の object がエントリ上限を超える場合、remote に書き込む前に `too_large` で拒否します。
大きいバイナリには `SaveBinary` / `PutBlob` を使えます。

`RemoteError::is_retryable()` と `SyncError::is_retryable()` で、
`locked` / `unavailable` を再試行可能なエラーとして判別できます。
待ち時間と再試行回数はホストが決め、他のエラーは利用者に伝えます。

コミット ID を指定した `ListObjects` / `ReadObject` でスナップショットを、
`Log` / `Show` でコミット履歴を、`ReadBlob` でバイナリを読めます。
object の応答には text、record JSON、conflict の項を含みます。

デフォルトの feature `bundled-sqlite` は SQLite を同梱します。
組み込む側は default features を無効にし、必要に応じて `store` / `rust-digest` を選べます。
`DirRemote` / `ProcessRemote` は native 専用です。
wasm では `Remote` / `MemoryRemote` とプロトコルの型を利用できます。
